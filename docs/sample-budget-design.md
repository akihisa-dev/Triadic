# 三面運輸のサンプル予算設計

この文書を、配布する確認用データの業務設定・数値前提・機能との対応の正本とする。アプリ機能を変更するときも参照し、影響があれば設計→生成元→実ファイル→検証の順に更新する。単発の作業報告ではなく、次回の更新に使う設計文書である。

製品仕様の正本は[REQUIREMENTS](../REQUIREMENTS.md)、実装範囲は[README](../README.md)。ここでは実装済み機能だけを用い、製品仕様を書き換えない。名称・荷主・単価・人数・金額は架空であり、実在企業の予算や市場相場を示すものではない。

## 合意した会社設定と優先順位

- 社名は三面運輸。既存事業は百貨店・専門店向けのアパレル配送とアパレル倉庫。
- 月商約10億円。輸送5億円のうちルート配送4億円、チャーター配送1億円。倉庫5億円。
- 東京圏、大阪圏、名古屋圏、福岡圏、仙台圏、札幌圏、中四国圏で営業。東京が最大で、東京・大阪・名古屋が主力。
- 現在は黒字。人手不足、機械化・IT化の遅れが将来の成長を妨げると見込み、先行して改善する。
- 顧客を多様化し、既存荷主への依存を下げる。新規事業は衣料品以外の物流とする。機械化による省力化、AIによる間接費圧縮も進める。
- 5か年計画の**2年目の1年間**を収録する。現在の利益水準を維持する。複数年の構想を全部この年度に実施しない。
- 施策数、科目行数、ファイルサイズに目標・下限・上限を設けない。分類の全組合せを埋めず、同じ施策の名称差替えによる水増しをしない。必要な定常費や同じ契約に由来する一定額は自然な反復として認める。

以下の数値、荷主名、月、契約条件は、この合意を具体化した設計上の仮定である。合意と仮定を混同せず、更新時に相互の整合を確認する。

## 年度と5か年計画

配布ファイル名は `2027年度サンプル予算.triadic` とする。配布サンプルは「2027年度サンプル予算」とし、2年目の基準年度Yを2027に固定する。対象期間は2027年4月〜2028年3月、前年は2026年度（1年目）。生成日が変わっても年度を自動で繰り上げない。生成元の `BUSINESS_SAMPLE_FISCAL_YEAR` を年度の指定元とし、表示名・設計書・実ファイルを一致させる。アプリの通常の新規作成は従来どおり当年度を初期値とする。

## 保存する分類

部署は7圏域と本社の8件とし、部署マスタだけを会社設定に合わせる。部署以外のマスタは製品のデフォルトをそのまま使い、エージェントの判断で名称・コード・属性・構成・所属・並び順を変更せず、追加・削除もしない。この条件を満たすために製品側のデフォルトを書き換えることも禁止する。利用者が製品上で行うマスタ編集には制限を加えない。

「ルート配送」「チャーター配送」「アパレル倉庫」「非衣料品倉庫」「本社管理」は業務の説明であり、業種マスタの名称ではない。既存の業種には次のように割り当てる。

| 業務上の説明 | デフォルトの業種コード・名称 |
|---|---|
| ルート配送 | 1 直営自動車 |
| チャーター配送 | 2 自動車取扱 |
| アパレル倉庫の保管・入出庫・店舗出荷受託 | 4 不動産B |
| 非衣料品倉庫の保管・入出庫・店舗出荷受託 | 4 不動産B |
| 本社の営業費用 | 8 一般管理費 |
| 本社の営業外収益・営業外費用・設備借入利息 | 9 営業外 |

利用者の指定により、3 不動産Aはテナントへの賃貸収入、4 不動産Bは営業倉庫として扱う。三面運輸の倉庫事業は荷主の商品を預かり、保管・入出庫・店舗出荷を受託する営業倉庫であり、衣料品・非衣料品とも4 不動産Bに計上する。荷主分野の違いは施策名・備考で説明する。テナントへの賃貸収入は今回の会社設定になく、3 不動産Aに収支を作らない。3 不動産A、5 納品代行、6 雑作業、7 業務費Bのマスタ自体はデフォルトのまま残す。7圏域の部署は業種1・2・4に、本社は8・9に所属する。輸送はルート便を自社運行主体の1、チャーター便を協力会社手配主体の2で管理する設計上の仮定であり、ルート便の下払費用とチャーター便の一部自社対応費用も各契約に含める。無関係な全組合せに前年値や施策を作らない。

初期の57科目・15集計・8展開・6展開区分・9業種・期間・種別を維持する。科目属性と金額項目の固定定義も変更しない。科目は現行の意味で使い、実際に使用しない科目は0のままとする。下払運賃等は費用属性で、売上原価属性の社内控除科目へ外注費を入れない。全社の売上約120億円は、外部荷主への売上である。

荷主・拠点・資産・人員の独立したマスタは現行アプリにない。これらは施策名・備考とこの設計書で説明し、独自の保存列を追加しない。会社名の専用保存欄もないため、設計書と代表施策の備考で三面運輸を識別する。

## 利益と資金の整合

前年実績を基準にした一次予算は売上12,698,561,000円・営業利益838,176,225円・経常利益830,376,225円。確定予算は売上12,664,496,000円・営業利益812,791,225円・経常利益804,991,225円。前年利益を維持するのは年間額の条件で、全月の増益を強制しない。確定で新倉庫が遅れた分の減益を残す。

確定予算の衣料品以外の新規売上は計600,800,000円。既存荷主の運賃値上げや大阪→名古屋の移管を新規顧客売上に数えない。新規依存を1社へ集中させず、9荷主・複数地域・輸送/倉庫に分散する。具体的な荷主別売上全件を保存する機能はないため、全社の荷主別依存率を実ファイルだけから検証可能とは扱わない。

今期の設備取得は関東第一倉庫120,000千円、大阪仕分け36,000千円。前者は10月の借入120,000千円、後者は自己資金を想定する。取得代金156,000千円と借入元本は資金計画上の前提であり、損益の費用行へ重ねて計上しない。新倉庫の家賃・人員・準備費は上記予算に含む。資金繰り表や税務上の償却計算はアプリの未実装範囲であり、ここでは管理上の60か月定額配賦を用いる。

## 一次・確定・履歴

一次と確定は同じ年度の二つの予算。確定の記録がない月は一次を引き継ぎ、延期月の0は明示値として保存する。契約合意済みの東京4月は同額の確定値を持つ。

3時点の履歴では東京運賃是正を1月20日の2.6%、2月20日の2.8%、3月20日の3.0%へ改訂する。他の業務設定・前提・施策は共通とする。未設定画面や人工的な検証施策を履歴だけに埋め込まない。履歴は複数年度の予算ではなく、同じ2年目予算の検討過程である。

## 現行機能との対応と受入条件

機能ごとの操作・期待結果・実施状況は[samples/README.md](../samples/README.md)を参照する。正常な主ファイルに合わない境界値・失敗系は既存の小規模データと専用テストへ割り当てる。主ファイルに全条件を押し込むことを「全機能対応」としない。

- 前年実績の年間売上120億円、輸送/倉庫50:50、輸送内80:20、地域順位を独立計算する。実ファイルと全履歴で、倉庫の前年値・全施策を4 不動産Bへそろえ、不動産Aにテナント収入がないことを確認する。業種別の総原価表も独立計算と照合し、全社合計だけの一致で分類誤りを見逃さない。
- 全月の総原価表・展開表・施策一覧・上期/下期/通期を、保存入力値から製品計算を使わず算出した期待値と照合する。前年見込/実績、一次/確定を両方確認する。
- 開設前の売上・変動費・償却の先取りがなく、先行家賃・給与が残ることを確認する。将来拠点の営業金額を混ぜない。
- 前年10月・11月の既存施策と今期期間差を合わせた通年化、移管の全社相殺、同額・0の確定値、1円単位の精度を検証する。
- 生成→再読込→再生成一致、実ファイルと3履歴の保存形式・参照・分類・データ整合を確認する。部署以外のマスタの全定義列を新規ファイルのデフォルトと照合し、相違があればサンプル検証を失敗させる。独立した新規ファイル間で異なる作成識別子は定義値の比較から除き、生成処理内では初期化後の識別子も含めて変更を検出する。
- 件数やサイズを成功条件にしない。検証のための名称差替え施策を拒否する。

## 継続更新の手順

1. 機能変更時は製品方針・実装・保存形式・既存テストを確認し、この設計と機能対応表への影響を判断する。部署以外のデフォルトをエージェントが独自に変更しない条件を最初に確認する。
2. 会社設定・5か年計画・自然さを保持し、変更した機能に必要な前提、施策、保存項目、確認操作、期待値を更新する。影響がなければ業務データを増やさず、既存データを使う検証先を対応表に記載する。
3. [生成元](../tests/ui/sample-plan.ts)から呼ぶ[会社予算生成](../tests/ui/sample-business.ts)・[施策定義](../tests/ui/sample-portfolio.ts)を更新する。生成済みSQLiteを直接編集しない。
4. 前年比・地域別・事業別・契約数量・人数・月割り・設備費/償却・移管・一次/確定を再照合し、数値に影響する場合は設計書の期待値と独立テストを更新する。試験を通す目的だけで期待値を変更しない。
5. 既存ファイルが生成元と一致するか確認し、利用者の編集があれば別名コピーで保護する。`npm run samples:generate`、`npm run samples:check`、`npm run verify`を実施する。
6. 表示・操作に影響がある場合はCodex内ブラウザで確認する。Excel出力/取込に関わる変更時だけ対応する追加検証を実施する。
7. 設計書・生成元・テスト・対応表・必要な説明を同じ目的のコミットに含める。`.triadic`はローカルだけに保持する。

コピー・切り取りの確認には既存の月額・確定手修正・分類・小計を使う。業務設定・予算値・保存項目は変更しない。重なる移動と失敗時の元値保持、表示順と画面外の中間行のコピーは専用の画面テストで確認する。
