# データの時点履歴の設計

利用者向けの動作は[製品要件](../REQUIREMENTS.md#データの時点履歴)、使い方と制限は[README](../README.md#データの履歴)を正本とする。履歴は同じ`.triadic`内でデータ全体を記録し、通常の画面で内容を確認してから復元できるようにする。

## 保存構造

[現在の保存形式](../DATA_MODEL.md)は新規作成時から必須の履歴管理表を持つ。開く際には変更せず、最初のデータ変更の保存に変更前の記録を含める。次の識別子が1の場合だけ初回記録を行い、全件削除後に初回へ戻さない。

| 保存先 | 内容 |
|---|---|
| `data_history` | 削除後も再利用しない識別子、UTCの記録日時、履歴表を除いたSQLiteのデータ全体 |
| `data_history_state` | 履歴管理の版1、次の識別子、最初の未記録の保存日時、最新のデータ保存日時 |

履歴の作成では、検証済みの専用接続に付属するメモリDBへ正規の業務スキーマを作り、業務テーブルと採番状態（`sqlite_sequence`）だけを`INSERT SELECT`で転記する。形式情報の`document_type`を`snapshot`にし、業務DBだけを書き出して、完成した記録を`openBusinessSnapshot`で全体検証する。通常ファイルの`plan`と業務snapshotは別の検証入口を使う。履歴を含む全体コピーや、作成時の履歴表削除・不要領域の圧縮（`VACUUM`）は行わない。過去の履歴を各記録へ複製しないため、容量の増加は業務データの大きさと記録件数に応じる。旧方式との比較と測定範囲は[業務スナップショットの比較](business-snapshot-performance.md)を参照する。追加の依存パッケージ・拡張権限・通信は不要とする。

日時・識別子・管理版・SQLiteの識別情報はファイル読込時に検証する。個々のデータの全体検証は選んだ履歴の読込時に行い、現在のデータと同じ年度であること、履歴を入れ子に含まないことも確認する。大量の記録を開くたびにすべて復号・展開しない。

## 記録と保存境界

通常・集計・種別選択のデータ更新は、編集後に`prepareSave.ts`の共通処理で取消用の状態・履歴の未記録状態・検証済みの保存内容を準備し、`writePreparedPlanChange`で確定する。通常編集は比較と適用を一回だけ行い、無変更なら履歴も表示用データも作り直さない。履歴の記録・復元・削除と操作取消は、準備済み履歴の扱いを指定して`writePlanChange`から同じファイル確定境界へ進む。初回は変更前の状態も準備する。保存先の外部変更を確認し、書き込みと確定の成功後だけ現在のデータを置き換える。失敗した更新の履歴だけが残る状態にはしない。

`usePlanSession`は保存済みの未記録日時から5分の期限を求める。一連の保存で期限を延ばさず、同時のファイル処理があれば終了後に記録する。記録中に始まった自動保存はその書き込みの後へ直列化し、入力を失わない。タイマーが遅れた場合は、実行時点の保存済みの状態を記録する。

正常なファイル終了と過去閲覧への切り替えでは5分を待たず未記録分を残す。履歴管理だけの変更は新たな業務データ変更として記録しない。記録失敗では期限と元データを保持し、自動で書き込みを繰り返さず、次の保存成功または利用者の再試行で再開する。

タブ終了・再読み込み・強制終了で非同期書き込みの完了は保証できない。通常のデータ保存は既存どおり確定し、未記録の開始日時はファイルへ残るため、開き直した際に期限を確認できる。

## 閲覧・復元・削除

現在のデータと閲覧用の過去データは別の状態として保持する。共通の閲覧専用状態を各編集画面へ渡し、入力・保存・削除・並べ替えを禁止する。画面移動と種別の閲覧、図の移動・拡縮は維持する。切り替え時は編集部品を作り直し、前の編集内容や選択済み施策を別の時点へ持ち込まない。現在へ戻るだけなら登録前の下書きは保持する。

復元では選んだデータ全体のコピーに現在の履歴管理表を引き継ぐ。復元前の現在状態と復元した状態を追加し、データ保存と同じ失敗・競合確認を通す。成功後に現在のデータを置き換え、下書きと画面移動履歴を初期化する。失敗では閲覧中の過去データと現在のデータを維持する。

削除は識別子の集合か、指定日時より前の条件で行う。複数件の削除は一つの処理で確定し、対象が消えていた場合は部分削除しない。利用者による履歴削除後は`deleteDataHistory`で不要領域を詰める（`VACUUM`）。これは履歴作成とは別の処理であり、業務データ・未記録期限・次の識別子を維持する。

## 実装境界と検証計画

1. `core/storage/dataHistorySchema.ts`と`core/storage/dataHistory.ts`で記録・検証・復元・削除を完結させる。初回記録、5分の境界、期限維持、全体復元、新しい履歴の保持、破損・年度違い・入れ子の拒否を通常テストで確認する。
2. `extension/PlanSession.ts`が保存済み状態と処理順を管理し、`preparePlanCommand.ts`で業務更新と取り消し用の状態を準備する。`planFile.ts`で実ファイルへの確定・競合、`usePlanSession.ts`でタイマー、`PlanSession.ts`で終了を扱う。書込・確定失敗、保存許可、再試行と同時入力を確認する。
3. `DataHistoryPage`、`workspace/useWorkspaceHistory`、`useHomeWorkspace`、`HomePage`に履歴入口・日時一覧・削除確認・過去閲覧・復元確認を設ける。広い画面と狭い画面で、すべての編集入口の禁止と通常閲覧を確認する。
4. 確認用データへ内容の異なる3時点を追加し、実ファイルの再読込と生成元の一致を検証する。既存の金額・集計・分類・手修正の確認条件を維持する。

必須の検証とコミット手順は[AGENTS.md](../AGENTS.md#検証と完了条件)に従う。サンプルの条件と確認範囲は[対応表](../samples/README.md#履歴の確認)で管理する。
