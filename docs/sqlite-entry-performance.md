# 入口画面のSQLite初期化の比較

Issue #79で、履歴の型・空状態・5分の間隔をSQLiteに依存しない定義へ移しました。通常のWorker対応ブラウザの入口画面ではSQLiteを初期化せず、データ処理で必要になる専用Workerが初期化します。

`OPEN_BASELINE=3305d39 OPEN_EXPECT_WINDOW=0 node scripts/measure-file-open.mjs`で変更前と現在のソースを比較します。前回の一括読込の修正を両方に含め、今回は定数経由の初期化だけを比較しています。観測はViteの本番モードで構築した一時ビルドに挿入し、配布物には含めません。計測用WorkerはES形式です。

macOS、Apple M6、Chrome 154.0.8037.98、Node.js 26.4.0、React 19.3.0を使用しました。ファイルと段階別の測定方法は[file-open-performance.md](file-open-performance.md)と共通です。個人の実ファイルは操作していません。各条件ごとに新しいブラウザ環境で初回1回と、キャッシュのある再起動5回を観測しました。再起動ではWorkerも新しく作ります。

## 初期化の実行回数

すべての条件・すべての反復で、ファイルを開く前のWorker初期化は0回でした。変更前は画面側でSQLite初期化が1回始まり、変更後は0回でした。最初のファイル読込でWorker側の初期化は前後とも1回です。画面側の初期化を後回しにしているのではなく、通常画面から除去しています。

初期化は`initializeSqlite`の実行から実ローダーを初めて呼ぶ箇所で観測しました。単なるファイルサイズやリソース参照の数ではありません。静的な依存の自動テストでも初期画面からSQLite実装と履歴保存実装へ到達しないこと、Workerが実SQLiteと同じ履歴定義を使うことを確認しています。Nodeの直接実行経路は標準検証で確認しています。

## 正確性と確認範囲

画面に公開された計画・履歴の検査用ハッシュは前後・全反復で一致しました。前後ともファイル読込の依頼と完全検査は1回です。版検査・正規スキーマの検査・金額と参照の検査は変更していません。履歴の空状態と5分の定義は一つだけです。

`npm run verify`、広い画面と狭い画面での通常読込・新規作成・続きから・ドロップ、保存・取消・履歴復元、Worker失敗後の再試行を確認しました。実Workerの起動用スクリプトを一度だけ失敗させる確認では、元ファイルと前回参照を保持し、次の選択でWorkerを再作成して開けました。入口でSQLite本体を取得せず、正常な読込で必要になる本体を取得することも確認しています。Codex内のブラウザでも入口の表示と操作可能状態を確認しました。

時間は観測処理、自動操作、画面の遷移と描画待ちの影響を含みます。DOM表示は画素の描画完了時刻ではありません。入口はSQLite初期化の完了を直接待たない従来の設計であり、変更前の表示が必ずSQLite完了まで止まっていたとは解釈しません。最大メモリ、機器全体の冷えたキャッシュ、利用者の実ディスク、実際のWASM初期化自体の故障からの回復は今回追加で測定していません。起動時間の保証やアプリ全体の短縮率には扱いません。
