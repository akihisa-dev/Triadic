# 通常保存の性能測定

通常保存での完全検査を維持し、同じ結果の計画・履歴の二重読み取りだけを一回にまとめました。外部ファイル、更新前後、操作取消用データ、履歴復元時の検証は変更していません。保存形式25を維持します。

## 再現と条件

`node scripts/measure-save-performance.mjs > /tmp/save-performance.json` で再現できます。製品コードは変更せず、専用の一時ビルドにだけ検査の時間測定を挿入します。施策数10・100・500、各施策に1行×12か月、履歴0・4・11件の合成計画を使用します。保存前のサイズは順に417,792・2,269,184・8,298,496バイトです。初回変更では変更前の時点履歴が追加されます。

2026-10-11、macOS arm64、Apple M6、Node 26.4.0、SQLite 3.53.4。変更前は4d2b877、変更後は今回の共通読み取りです。各条件でウォームアップ1回の後に5回測定しました。並行した検証やビルドを停止して比較しました。時間はms、中央値（最小〜最大）です。

検査と書き出しの回数は3種類の更新命令で同じでした。履歴0件の変更では計画の完全検査10→9回、コピーの完全検査3回、整合性・参照検査13→12回、SQLite書き出し5回です。履歴4・11件では計画9→8回、コピー2回、整合性・参照検査11→10回、書き出し4回です。ファイル読み取り・書き込み・確定は各1回です。

通常の施策・前年・科目更新は、変更適用、取消用の前後コピー、時点履歴付与、保存結果の読み取り、保存先照合、書き込み確定の順に進みます。履歴がない最初の変更では、変更前のコピー作成と初期履歴保存が追加されます。書き出し自体より完全検査に時間がかかりますが、不正なファイルを検査済みとみなす仕組みは導入せず、最後の同一結果の二重読取だけを削減しました。

500施策では約5〜7%短縮しました。小・中量では範囲が重なる条件があり、一律の速度改善とは評価しません。残る検査の削減は安全性への影響が大きく、今回の測定だけを根拠には実施しません。

## 確認範囲と制限

ファイル境界は専用のNode一時ファイルへの読み書き・renameで代替しています。Chromeの実ファイル保存、許可取得、端末ストレージの差、画面の体感時間は測定していません。合成計画の件数は製品全体の性能保証ではありません。一時ファイル・ビルドは終了時に削除し、利用者のファイルには触れません。

共通読み取りのテストは、従来の計画・履歴の読取結果との一致、元データ保持、破損・旧形式・不正値・不正参照・不正履歴状態・履歴内部用データの拒否を確認します。標準検証では保存失敗・競合・再試行・操作取消・時点履歴復元・参照専用操作の保護も確認します。
