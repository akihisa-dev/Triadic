# Triadicの全面リファクタリングに関する補足

共通の調査・改善・進行・報告手順は明示的に使うプラグイン側で管理し、本スキルはTriadic固有の契約と承認条件を補う。

製品判断は[REQUIREMENTS.md](../../../REQUIREMENTS.md)、作業・権限・検証・コミットは[AGENTS.md](../../../AGENTS.md)、実装済み範囲とコマンドは[README](../../../README.md)に従う。

## 依頼の扱い

- 対象はアプリ全体のすべて。構造、状態とデータの流れ、画面内部、計算、保存、履歴、安全性、性能、依存ライブラリ、生成・検証・文書を横断する。必要なら内部を全面的に作り直し、既存の骨格へ合わせることを優先しない。
- 全面リファクタリングの実行依頼では、全体調査と設計を行い、利用者の明示的な承認後に呼び出し元の移行、検証、置換後の整理、必要な文書更新と通常コミットまで進める。
- 調査・設計・レビューだけの依頼では読み取りと設計を行う。設計結果から実装の許可を推定しない。
- 対象や除外が指定されていれば保持する。全体の依存関係を調べることと、対象外を編集することは別である。
- 現在の機能・表示・操作・保存データ・受け付けるファイルを維持する。依存ライブラリと開発・検証の仕組みは、必要性と効果を裏付けられる更新・置き換えも設計対象にする。
- 既存の不具合は勝手に修正しない。[判断を仰ぐ報告と分担](references/decisions-and-review.md)に従い、専門知識がなくても判断できる説明を行う。要件の未実装、要件と実装の矛盾、今回の変更による不具合を区別する。


## 全体読解と設計承認の条件

このプロジェクトの全面リファクタリングでは、[全体調査と検証](references/full-scan-and-verification.md)に従って隠しフォルダを含む全体を棚卸しし、自作コード・CSS・設定・スクリプト・テスト・文書を全文確認する。全文検索や件数だけで読了とせず、未読・未確認・読み取り失敗を残して全体調査完了としない。

全体設計の明示的な承認を得るまで、製品ソース・依存・設定・生成物を変更しない。実行依頼やスキル呼び出しを設計承認とみなさない。[判断を仰ぐ報告と分担](references/decisions-and-review.md)に従い、設計のみ・承認済み範囲・判断待ちを区別する。

調査・独立レビューは利用可能なサブエージェントに読み取り専用で分担し、編集・統合・検証コマンド・Git操作は主担当が行う。他チャットへの連絡、ブランチ作成、並行編集の許可へ広げない。

## 設計で照合する固有の境界

[再構成の設計](references/architecture.md)で、保存済み計画、未保存入力、履歴閲覧、画面移動、表示位置の所有者と寿命を確認する。金額・種別の規則、表の計算、SQLiteの読込・検証・更新、実ファイルへの確定を分け、coreとextensionの境界を保つ。

マスタの固有制約、CSSの順序・動き、拡張入口、生成物の責任を維持する。データベースの開閉・検証・export、byte複製、再計算・描画・購読の増減も比較し、通常操作の負担を増やさない。依存の更新・置換は承認された設計と依存管理規則の範囲に限る。

## 移行と検証

独立した目的ごとにコミットし、途中で正常に使えない状態を完了コミットとして切り出さない。責任の移動と全呼び出し元の移行、旧関数・型・イベント・タイマー・CSS・動的参照・Manifest・ビルド・テスト・文書の再照合を同じ変更単位で完了する。保存契約や利用先が残るものは消さない。

[全体調査と検証](references/full-scan-and-verification.md)の製品別比較表と検証条件を使う。既存の不具合、仕様の未実装、今回の回帰を分け、失敗を隠す検査の削除・期待値変更をしない。承認された範囲の移行・検証・正本文書・生成物・版の一致と通常コミットが揃うまで実装完了にしない。
